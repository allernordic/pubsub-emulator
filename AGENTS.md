# AGENTS.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm t` / `npm test` — runs Mocha (mocha-cakes-2 BDD UI) and on success also runs `lint`, `build`, `test:types` and `test:md` via `posttest`.
- `npm run lint` — `eslint . --cache` followed by `prettier . -c`.
- `npm run build` — `dts-buddy` regenerates `types/index.d.ts` from JSDoc, then `npm run toc` rewrites the README table of contents between the `<!-- toc -->` markers (`scripts/toc.js`, copied from google-secret). There is no transpile/bundle step: Node `>=22` is required (`.nvmrc`) and `require()` of the ESM source works natively, so the package ships `src/` as-is.
- `npm run test:md` — executes the README's ` ```javascript ` code blocks with `texample` (via `scripts/texample-setup.js`, which exits explicitly since examples leave fake servers bound). texample host-imports specifiers, so all blocks share one module graph — the broker singleton carries seeded state from the prefill example into the inspect example, and README examples are order-dependent. Only ` ```javascript ` fences run, never ` ```js `.
- `npm run test:types` — `tsc -p .` (src, strict checkJs) then `tsc -p test` (tests; requires built types since they import the package by name). Runs after `build` in `posttest` — dts-buddy does NOT surface all tsc errors (e.g. implicit any), so tsc is the authority.
- Run a single test file: `npx mocha test/features/topics-feature.js`. Filter by name: `npx mocha -g 'pattern'`. Bail on first failure: `npx mocha -b`.
- `npm run cov:html` / `npm run test:lcov` — coverage via `c8`. Held at 100% statements/lines/functions; the only uncovered branches are three defensive fallbacks the Node client never triggers (StreamingPull double-subscribe guard, `maxOutstandingMessages || 1000`, `publishTime.nanos ?? 0`) — treat NEW uncovered branches as either a missing test or dead code to remove.
- Server debug logging: `DEBUG=aller:pubsub-emulator* npx mocha`. gRPC-level: `GRPC_TRACE=all GRPC_VERBOSITY=DEBUG`.

No TLS certs or auth setup is needed — the Pub/Sub client treats a custom non-GCP `apiEndpoint` as an emulator and switches to insecure channel credentials, which also skips auth.

## Architecture

`@aller/pubsub-emulator` is an in-memory fake of the Google Cloud Pub/Sub gRPC API (`google.pubsub.v1` `Publisher` + `Subscriber` services) for use in tests, modeled on the fake server in the sibling repo `../google-secret`. The whole server is `src/index.js` (plus `src/rpc-codes.js`); the package name says it all, so there is no subpath export or re-export layer.

- **Proto-backed gRPC server** — the real `pubsub.proto` is loaded from the installed `@google-cloud/pubsub` package (with `google-gax` include dirs, resolved via `createRequire` since google-gax doesn't export its package.json), so requests/responses are serialized exactly like the real API. Unimplemented RPCs (snapshots, seek, update) fall back to grpc-js UNIMPLEMENTED.
- **Per-server smqp broker is the source of truth** — the services are classes (`FakePublisher`, `FakeSubscriber`, both exported) constructed with a broker; `startServer` creates a fresh broker per server (or takes a prefilled one via `options.broker`), so parallel servers are fully isolated. Handler methods need no manual binding — grpc-js `addService` binds each handler to the implementation object itself. Per-broker id counters live in a module-level `WeakMap` keyed by broker (shared between both services so publish and dead-letter message ids can't collide). There are no metadata maps: a topic is a smqp _topic exchange_; a subscription is a _queue_ bound to its exchange with `#`. The `Topic`/`Subscription` proto resources and the per-subscription `outstanding` ack Map ride on `exchange.options.topic` / `queue.options.subscription` / `queue.options.outstanding` (smqp options accept arbitrary keys). Existence checks go through `broker.getExchange`/`getQueue`; listings enumerate `broker.getState()`.
- **Auto-create (default ON)** — production topology is usually pre-provisioned, so by default `Publish` auto-creates a missing topic and `Pull`/`StreamingPull` auto-create a missing subscription. A pull request only carries the subscription name, so the auto-created subscription binds to a **same-named topic** (auto-created too, order-independent); differently named bindings must be prefilled. Invalid names still get `NOT_FOUND`, and creation reuses the lazy metadata synthesis (plain `assertExchange`/`assertQueue`/`bindQueue`). `startServer({ autoCreate: false })` restores strict `NOT_FOUND` behavior — the api-validation feature runs against a strict server for exactly that reason.
- **Prefill** — because the broker is the source of truth, tests seed state with the plain broker API: `broker.assertExchange(topicName, 'topic')`, `broker.assertQueue(subName)`, `broker.bindQueue(subName, topicName, '#')`, `broker.publish(topicName, 'message', content)` — either on a `new Broker()` (re-exported from smqp) passed to `startServer({ broker })`, or on `server.broker` after start. Missing proto metadata is synthesized lazily by `getFakeTopic`/`getFakeSubscription` (which also force `autoDelete: false` so prefilled entities survive consumer churn; a synthesized subscription finds its topic via bindings, else `_deleted-topic_`). Raw broker-published content (Buffer/string) is normalized to a pubsub message by `toPubsubMessage`, using smqp's auto `properties.messageId`.
- **Ack ids** — a counter; the `outstanding` Map (ackId → smqp message) tracks delivered-but-unacked messages. Unary Pull uses `queue.get()` (message stays in queue, flagged pending, until acked); StreamingPull creates one `broker.consume` consumer per open stream. ModifyAckDeadline with `ackDeadlineSeconds: 0` = nack + requeue (redelivery); non-zero deadlines are no-ops (the fake never expires outstanding messages).
- **Dead-lettering** — `deliveryAttempt` counts _nacks_ (+1), stored as `nackCount` on message `properties` since properties survive smqp requeue while the message instance does not. Counting nacks instead of deliveries is deliberate: stream-teardown churn redelivers messages across the client's 5 closing streams, and delivery-based counting would dead-letter spuriously on close. When a nack hits `deadLetterPolicy.maxDeliveryAttempts` (`|| 5`), `deadLetter()` forwards: a fresh publish to the dead-letter exchange (new message id, original attributes + `CloudPubSubDeadLetterSource*` attributes) and the original is acked. Missing dead-letter topic → normal requeue (keeps retrying, as real Pub/Sub). smqp's native `deadLetterExchange` option is NOT used — it forwards content verbatim and can't stamp attributes/new id.
- **The stale-ack race (important!)** — the Node client closes its streaming pulls _before_ flushing acks (and removing the last `'message'` listener closes streams immediately). Stream teardown cancels the smqp consumer with requeue, and smqp requeue creates a **new** Message instance, so a late ack holds a stale reference. Therefore gRPC-published messages carry `properties.messageId`, and a late ack finds the requeued copy by messageId and removes it with `queue.ack(copy)` — `message.ack()` cannot be used there since it silently no-ops on undelivered messages. Don't "simplify" this away; the streaming-pull feature covers it.
- State lives on the server's broker and dies with it — there is no `reset()`; tests just `server.forceShutdown()` in `after`. `server.getTopic(name)` / `server.getSubscription(name)` expose fake state for assertions (`getSubscription` returns `{subscription, outstanding, queue}` — note `queue.messageCount` includes delivered-but-unacked messages). All exports are named; there is no default export (dts-buddy drops a named export that is also default-exported).

## Testing conventions

- TDD in BDD style: write the failing feature spec first, then implement. `mocha-cakes-2` UI — `Feature` / `Scenario` / `Given` / `When` / `Then` / `And` are globals (declared for eslint in `eslint.config.js` and for tsc in `test/global.d.ts`); `expect` comes from `chai/register-expect.js` (`.mocharc.json`). Files live in `test/features/` named `*-feature.js`.
- Tests import the package by name (`@aller/pubsub-emulator`) via Node package self-reference — never by relative `../src` paths.
- Tests run the real `@google-cloud/pubsub` client against the fake server in-process: `new PubSub({ apiEndpoint: 'localhost:PORT', projectId: 'test-project' })`. Unary pull/ack uses `v1.SubscriberClient` with explicit `sslCreds: grpc.credentials.createInsecure()`.
- In streaming tests, ack/nack **inside** the message handler while the stream is open, and prefer `subscription.on('message', ...)` over `once` — `once` removes the last listener on first delivery, which closes the client's streams before acks are sent (see stale-ack race above).

## Style

Same as `../google-secret`: Prettier 2-space, 140 cols, single quotes, ES5 trailing commas. ESLint enforces import ordering (`builtin → external → internal → parent → sibling`, alphabetized, blank line between groups) — `npm t` fails in `posttest` on violations.
